| 模块 | 职责 | 蓝本对应 |
|---|---|---|
| `capture/` | 主线程捕获稳定根状态、续用戳 | `Runtime/CombatRootSnapshot`、`ContinuationStamp` |
| `sim/` | **影子状态**（纯数据）：玩家/怪物/牌堆/能量/能力/遗物计数 + 命令时序 + Fork | `Engine/InCombat/Simulation` |
| `mirror/` | **方法镜像**：卡牌/能力/遗物/怪物 AI 的结算语义 + 覆盖注册表 + **显式拒绝** | `Engine/InCombat/Mirrors` |
| `search/` | 动作生成、Beam、去重、预算闸、并行分片 | `Search/` |
| `eval/` | 六维排序：战损 → 药水成本 → 成长 → 回合 → 消耗 → 结束 | `Search/RouteQualityPolicy` |
| `exec/` | 计划部署到实机、偏离重算 | `Runtime/SolverController` |
| `ui/` | 覆盖层：路线面板、进度、三按钮、设置 | `UI/SolverOverlay` |
| `api/` | 战前预测（本期仅定义） | `Prediction/` |
| `verify/` | **差分台架**：真机 vs 影子，逐字段比对 | `Testing/` |
| `diag/` | 结构化日志、问题包 | `Diagnostics/` |
| `bootstrap/` | ModTheSpire 入口、配置、生命周期 | `Runtime/Entry` |

**线程模型**（照抄蓝本）：主线程捕获根 → 后台线程在影子状态上并行搜索 → 主线程接收结果 → 原生入口部署 → 续用戳核对。**真机对象永远不进后台线程。**

## 4. 机制设计

### 4.1 为什么选「方法镜像」

蓝本原文：`Engine/InCombat/Mirrors/` 的职责是「**原版 Hook / Model 方法镜像**」，整体是「根快照 + 影子状态 + 克隆模型（写时复制）+ 方法镜像」的混合体。选它的三个理由：

1. **能上后台线程** —— 影子状态是自己定义的纯数据，不碰游戏对象，可以真正并行；「克隆后跑真代码」只能挤在主线程。
2. **可被自动验证** —— 影子与真机跑同一串动作，逐字段比对（见 §4.6），差异必暴露。
3. **与蓝本同构** —— 未来的机制、调参、社区经验都能直接搬。

代价：**要逐条重写规则**。这是本项目最大的工程量，也是最大的风险（§8）。

### 4.2 一次 `Bash` 在影子引擎里的样子

> `Bash`（重击）= 2 点能量，8 伤害 + 2 层易伤。易伤 = 受到伤害 +50%。

| 步 | 发生什么 |
|---|---|
| 1 | 主线程捕获根：玩家 72/80 血、3 能量、手牌 5 张、三个牌堆、随机数（种子+计数器）、怪物 44 血与意图 |
| 2 | 建影子状态：卡牌只留「ID + 是否升级」两个字段，其余数值从**卡牌镜像表**查 |
| 3 | 生成动作：`Bash` 可打出（能量够、有目标） |
| 4 | 结算：查 `CardMirror[Bash]` → 依次执行 `Damage(8)`、`ApplyPower(Vulnerable, 2)`、扣 2 能量 |
| 5 | 伤害管线统一处理修正：力量、虚弱（-25%）、易伤（+50%）、格挡扣减、荆棘反伤 |
| 6 | 动作入栈，直到本轮动作全部结算完 → 新状态：敌 36 血、易伤 2、能量 1、手牌 4 张 |
| 7 | 算状态指纹 → 查备忘录（转置表）→ 展开下一层 |

**关键设计：卡牌用「数据驱动的效果组合」而不是「一卡一个类」。**

| 类型 | 占比（估计） | 做法 |
|---|---|---|
| 纯数值卡 | ~60% | 一行声明：`Bash = damage(8) + vulnerable(2)`，由通用执行器跑 |
| 条件/计数卡 | ~25% | 声明 + 少量钩子（如「每有一张攻击牌 +2 伤害」） |
| 特殊机制卡 | ~15% | 手写镜像（Searing Blow 动态伤害、Snecko Eye 混乱费用、Frozen Eye 牌序、Runic Pyramid 保留手牌） |

**未知即拒绝**：任何没有登记镜像的卡/遗物/能力，在搜索时**拒绝该动作**或整场报「不支持」，绝不猜。这是蓝本的硬规则，我们照抄。

### 4.3 信息口径：全知（已定）

- 影子状态直接持有随机数（种子 + 计数器）与**有序牌堆**，推演时按确定性前进。
- 这不是作弊：杀戮尖塔的随机数是伪随机，复制状态后往前推就是唯一结果；真机的抽牌堆本来也是有序的。
- **M2 保留一次对照实验**：把牌序打乱、按 K 个世界采样（严格信息集），量化「全知到底多赚多少」。结论只作为数据记录，不改变默认。

### 4.4 执行与偏离重算

只执行**当前回合**的计划前缀，逐步通过游戏原生入口落地（动画音效正常）。每步前比对实机与预测快照（蓝本的「续用戳」）：一致则继续，偏离则中止重算。

### 4.5 界面与接口

- **覆盖层**：按回合分组的路线（出牌/目标/选牌/药水/结束回合）、预计整场战损、搜索进度、`重新计算 / 执行本回合 / 全自动`。
- **设置**：预算档位（低 60 秒/6 万节点 → 极高 300 秒/50 万节点）、并行度、通知。
- **战前预测接口**：给定牌组/遗物/药水/血量/遭遇/难度 → 预计战损。进程内直接跑一场影子战斗，不需要像蓝本那样另起游戏进程。

### 4.6 差分台架（本项目最重要的工程件）

影子模拟的正确性**不能靠人读代码**，只能靠自动比对：

```
真机走一步  →  记录动作 + 前后完整状态
影子走同一步 →  记录动作 + 前后完整状态
              ↓
        逐字段比对（血/能量/牌堆/能力层数/遗物计数/随机数计数器）
              ↓
        一致 → 打勾   ／   不一致 → 定位到字段与镜像条目
```

- **A1**：200 帧根状态捕获后，影子重建 → 与真机全字段 diff = 0
- **A2**：每帧跑 N 条随机合法动作序列，逐步比对 → 一致率 100%
- 这套台架同时是 §5 覆盖矩阵的**执行器**：每张卡、每个遗物、每个遭遇都是它的输入。

## 10. 蓝本核查（证据留档）

> 核查对象：`Torch1230/CombatSolver` 的 `docs/ARCHITECTURE.md` 与 `README.md`，以下为原文引用。

**10.1 用不用 Mirror？** 用，且是核心。`src/Engine/InCombat/Simulation/` 职责为「通用命令时序、历史、**RNG**、**牌堆**、伤害和 **Fork**」；`src/Engine/InCombat/Mirrors/` 职责为「**原版 Hook / Model 方法镜像**」。原文：「每项战斗语义只有一个权威结算实现。可变值由根快照、**影子状态**、**克隆 Model** 或 `PredictionStateStore` 持有……COW（写时复制）取得可写所有者后再写。」

**10.2 搜索跑在哪？** 后台线程。原文：「主线程捕获稳定战斗根 → 冻结请求政策 → **后台分支搜索** → 主线程接收结果 → 原版公开入口部署当前回合 → 续用戳核对或重新捕获。」「后台只读取根与分支状态；真实战斗对象只用作稳定身份或只读模型元数据。」

**10.3 是不是全知？** 是。① 模拟分支自持 RNG 与牌堆；② README「跨回合搜索：继续**预测抽牌、洗牌**、敌人行动」；③ 原文「**攻击意图由分支当前怪物 AI 行动派生**」。机制上是复制随机数往前推，不是读答案表。

**10.4 算不了的怎么办？** 显式拒绝。原文：「未知语义形成明确边界或失败」「未知 gameplay subscriber **显式拒绝**」。

**10.5 覆盖怎么管？** `CoverageCatalog` 读取 `catalog/classifications.json` 与 `evidence/test-evidence.json` 生成覆盖报告；`MethodMirrorRegistryDescriptor` 向覆盖目录暴露 registry 支持元数据。
